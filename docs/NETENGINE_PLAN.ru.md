# Сетевой слой как фундамент движка — дизайн-документ

> Статус: **реализовано** (решение и миграция завершены 2026-10). Цель проекта:
> построить на базе исходников полноценный игровой движок.
> Стратегия выбрана: **A — переписать сетевой слой с нуля** (см. `WORLD_SYNC_PLAN.ru.md`
> и решение в памяти проекта). Монолит `NetworkServer/NetworkClient` выпилен;
> весь транспорт/авторизация/валидация/релей теперь в переиспользуемом слое
> `src/game/netengine/`; `NetworkMatchManager` — тонкий мост.

## 1. Зачем переписать (проблемы текущего слоя)

Текущие `NetworkServer/NetworkClient/NetworkMatchManager` **работают** и покрыты
тестами (32/32), но как основа движка имеют структурные дефекты:

| # | Дефект | Следствие для движка |
|---|---|---|
| 1 | Типы пакетов — `enum 0..10` без версионирования | любое изменение пакета ломает совместимость клиент-сервер; нет реестра |
| 2 | Обработка пакетов — один большой `switch` | невозможно добавить свой пакет/событие без правки ядра |
| 3 | `NetworkMatchManager` смешивает транспорт, сессию и «мир» (провайдеры/remote-players) | сеть не отделима от игрового мира, нельзя переиспользовать в другой игре |
| 4 | Серверный Lua-АПИ (`ServerModManager`) — только 3 хука | не событийная модель; моды не могут полноценно расширять логику |
| 5 | Headless-сервер не имеет движка мира (моки) | ограничение надо осознанно описать, а не подразумевать |

## 2. Целевая архитектура (слои)

Сетевой слой движка разбивается на **независимые слои**, где каждый слой
работает через интерфейс, а не через конкретные классы.

```
┌─────────────────────────────────────────────────────┐
│  game (использует движок)                            │
│    GameplayContext → MatchSession ──;  Аvatar/world  │
└──────────┬──────────────────────────────────────────┘
           │ интерфейсы (pure virtual)
┌──────────▼──────────────────────────────────────────┐
│  net::Session (бывш. NetworkMatchManager)            │
│  - lifecycle: host/join/leave                        │
│  - состояние матча (id, players, seed)               │
│  - НЕ знает про мир — только сессия                  │
└──────────┬──────────────────────────────────────────┘
           │
┌──────────▼──────────────────────────────────────────┐
│  net::Endpoint (транспорт)                           │
│  - ServerEndpoint / ClientEndpoint (бывш. Server/Client)│
│  - реестр пакетов (PacketRegistry) вместо switch      │
│  - versioned protocol                                 │
│  - ping/liveness/auth                                 │
└──────────┬──────────────────────────────────────────┘
           │ ENet
┌──────────▼──────────────────────────────────────────┐
│  ENet (низкоуровневый транспорт)                     │
└─────────────────────────────────────────────────────┘
```

## 3. Ключевые компоненты нового АПИ

### 3.1 `net::Protocol` — версионирование и реестр пакетов

Вместо enum + switch — таблица «тип → описание пакета»:

- `PROTOCOL_VERSION` (u16) — мажорная версия он-вайр формата. Клиент предъявляет
  при HELLO; сервер отклоняет несовместимых.
- `PacketId` — `uint16_t`, зарезервированное пространство: `0x0000` системные,
  `0x0100` игровые, `0x0200` серверные Lua-события, `0x8000+` пользовательские.
- `PacketRegistry` — `map<PacketId, IPacketHandler*>`, без switch. Стороны
  регистрируют обработчики. Расширение = зарегистрировать новый id.

```cpp
class IPacketHandler { virtual void Handle(PeerId, const Packet&) = 0; };
class PacketRegistry {
    bool Register(PacketId, IPacketHandler*);
    bool Dispatch(PeerId, const Packet&);
};
```

### 3.2 `net::Packet` — буфер с типизированным полем

Заменяет ручные `WriteU32/ReadU32` + приёмники на безопасный буфер:

```cpp
class Packet {
    PacketId id; uint16_t payloadSize; uint8_t data[MAX_PACKET];
    // типизированный reader/writer (bounds-checked), little-endian
    bool WriteU16(uint16_t); bool ReadU16(uint16_t&); ...
    uint16_t SerializedSize() const;
};
```

### 3.3 `net::Session` — отделение от мира

Сессия (бывш. `NetworkMatchManager`) **не знает** про Avatar/Character/мир:
- только состояние матча: `PeerId selfId`, `PlayerList`, `worldSeed`,
  события `onPeerJoined/onPeerLeft`;
- мир подключается снаружи через **интерфейсы** (реализованы в
  `netengine/WorldInterfaces.h`):
  - `net::ILocalStateProvider` — «что разослать о себе» (читает живой avatar/vehicle);
  - `net::IRemoteStateSink` — «куда доставить состояние удалённого игрока/его
    машины/прыжка», плюс `OnPeerLeft` для очистки.
- пейлоад состояния переносится **opaquely** (байты + id) — сессия не
  разбирает игровой формат; десериализацию делает сам мир через sink.

### 3.4 `net::Endpoint` — транспорт без логики мира

`ServerEndpoint`/`ClientEndpoint` — ENet-обвязка + реестр пакетов + liveness/auth.
Gameplay-код вообще не трогает ENet.

## 4. Серверный Lua-АПИ → событийная модель

`ServerModManager` из 3 хуков расширяется до событийной шины:
- C++ издаёт события (`PlayerJoined`, `PlayerLeft`, `PlayerState`,
  `WorldSeedAssigned`, произвольные `GameplayEvent`).
- Моды подписываются функциями Lua (`events.on(PlayerJoined, fn)`), могут
  переопределять авторитетные решения (вернуть false/заменить).

Это делает мод-систему полноценной точкой расширения движка.

## 5. Миграция существующего кода (план)

Постепенная, без «большого взрыва»:
1. Завести новые модули `src/game/netengine/` (нетронутая область).
2. Перенести/обернуть существующие сущности под новые интерфейсы:
   - `NetworkPacket` → `net::Packet + PacketRegistry`
   - `NetworkServer/Client` → `net::ServerEndpoint/ClientEndpoint`
   - `NetworkMatchManager` → `net::Session`
   - `RemotePlayerWorldView/Manager` → `IRemotePlayerSink`
   - `ServerModManager` → событийная Lua-шина
3. `GameplayContext` подключает `Session` к миру через интерфейсы.
4. Удалить старинные хедеры после переноса.
5. Тесты переезжают на новые имена + новые кейсы (протокол, реестр, сессия).

**Решение по миграции (2026-10):** «сделать новое, потом выпилить старое» —
сначала полностью реализовать протокол на новом `netengine`
(welcome/seed/auth/player-list) + покрыть тестами, затем переключить
`GameplayContext` на `net::Session` через интерфейсы и в конце удалить старые
`NetworkServer/Client/MatchManager` одним разом. Старое не трогать до готовности.

## 6. Принятые решения

1. **Пространство имён:** `net::` (решение пользователя) — переиспользуется для
   нового АПИ; существующий `net::ENetInit` и LE-примитивы остаются частью этого
   неймспейса.
2. **Новые файлы с нуля:** `net::Endpoint` / `net::Session` / `PacketRegistry`
   пишутся как новые модули в `src/game/netengine/`; существующие
   `NetworkServer/Client/MatchManager` разбираются как эталон и переносятся, без
   сохранения старой формы.
3. **Lua-АПИ событийной модели** — после стабильных транспорт + сессия (этапность).
4. **Совместимость с текущими пакетами** не критична — формат можно менять, но
   фиксируется первая версия `PROTOCOL_VERSION`.

## 7. Критерий «готово» (задача 2)

- `net::Session`, `net::ServerEndpoint/ClientEndpoint`, `net::PacketRegistry`
  реализованы и покрыты тестами.
- `GameplayContext` подключен к `Session` через интерфейсы; старые `Network*.h`
  удалены или остались только как внутренние реализации.
- Протокол версионирован, реестр расширяем (тест «добавить свой пакет»).
- Спецификация этих модулей описана в `docs/` (этот документ входит в неё).
