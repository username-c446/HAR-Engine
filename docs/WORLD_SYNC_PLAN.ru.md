# Синхронизация мира в мультиплеере — стратегия A (детерминизм + общий seed)

> Статус: проект (design document). Дата: 2026-10.
> Выбор пользователя: полная видимость общего мира → реализуемо через детерминизм
> симуляции + единый seed, а НЕ через headless-сервер (у него нет движка мира).

Проект развивается как самостоятельный движок; ниже — дизайн синхронизации мира,
проектируемый на фундаменте сетевого слоя `net::` (см. `SPEC.ru.md`). Упомянутые
системы («трафик», «педы», «парковка», «интерьеры») — модули движка, которые
загружаются движком через интерфейсы мира.

## 1. Почему не «сервер судит мир»

Headless-сервер (`mp_standalone`) не грузит арт-данные уровня и мировой движок —
он работает через моки (`mp_network_fakes.h`), только принимает/ретранслирует
позиции сущностей. Поэтому авторитетом за динамикой мира (трафик/педы/пропсы/
миссии) он быть не может. Синхронизировать мир можно только с двух сторон:

- **A. Детерминизм + общий seed** (выбрано): оба клиента гонят один и тот же
  уровень с одинаковым начальным RNG-состоянием → генерируют одинаковый статический
  состав мира (какие модели трафика, цвета, педы, парковка, интерьерные пропсы).
- B. Серверная репликация полного состояния (отвергнуто: огромная нагрузка, лаг,
  масса пакетов; фактически новая подсистема).

## 2. Что показал аудит кода

### RNG-системы мира
| Подсистема | Источник | Случайность | Изменяет видимый мир |
|---|---|---|---|
| Трафик | `trafficmanager.cpp` | `rand()` ×8 (модель, цвет, спавн, пропуск) | да |
| Педы | `pedestrianmanager.cpp` | `rand()` ×6 (модель, тип, позиция) | да |
| Парковка | `parkedcarmanager.cpp` | `rand()` ×2 (модель, наличие) | да |
| Интерьеры | `interiormanager.cpp` | `rmt::Randomizer sRandom` (пропсы) | да |
| Миссионный спавн | `missionscriptloader.cpp` | — (скрипты фиксированы) | нет |
| Персонажи | `charactermanager.cpp` | — | нет |

### Seed
- `Game::GetRandomSeed()` = `(год<<16|месяц<<8|день) ^ (сек<<24|мин<<8|час)` — **wall-clock**, зависит от секунд.
- `srand(GetRandomSeed())` один раз в `win32main.cpp:244`.
- `sRandom.Seed(GetRandomSeed())` лениво в `interiormanager.cpp:2051`.

**Уязвимость:** если два клиента стартуют в разные секунды → разный `rand()`-seed
→ разный состав трафика/педов/парковки, миры расходятся. Даже в одну секунду —
точное совпадение вызовов `rand()` требуется по порядку (lockstep-чувствительно).

### Тикрейт
- Главный цикл: **переменный dt** (`game.cpp:483`: `elapsed = newTime - time`),
  идёт в `OnTimerDone(elapsed)`. Lockstep-физика (оба клиента байт-в-байт) НЕВОЗМОЖНА.

## 3. Доступный объём синхронизации (реалистично)

Полный lockstep отпадает (переменный dt). Стратегия A достигает **семантической**
синхронизации статического мира:

1. **Единый seed на всю сессию.** Сервер в начале матча выбирает seed (число) и
   рассылает его клиентам в `WELCOME`/новом `PACKET_WORLD_SEED`. Клиенты перед
   инициализацией мира вызывают `srand(worldSeed)` + `InteriorManager::sRandom.Seed`
   → одинаковые *статические* решения на всех клиентах.
2. **Порядок инициализации** уровня должен быть идентичен на клиентах (тот же
   уровень/миссия — уже так и есть: все подключаются к одному `L1/M1`).
3. **Движение** («динамика») — НЕ детерминируется: мир движется по локальной
   физике (переменный dt). Его позиции синхронизируются на верхнем уровне
   существующим реплеем (или остаются локальными расхождениями, терпимыми на
   ранней стадии).

## 4. Изменения в коде (план)

- `Packet.h` (netengine): ввести `PACKET_WORLD_SEED`/`PID_WORLD_SEED` (server→client,
  payload u32) — в текущей реализации уже есть `PID_WORLD_SEED` (0x0007).
- `net::Session`: при приёме seed клиент применяет его перед созданием мира
  (в точке инициализации мира), вызывая `srand(seed)`.
- `net::Session::StartHost`: выбрать seed (например `radTimeGetMilliseconds() &
  0x7FFFFFFF`), передать в сервер, разослать при welcome.
- Провайдеры сида мира: в мультиплеере возвращать/использовать сетевой seed,
  а не wall-clock (гейт по `IsInMatch()`).
- Точка инициализации мира: перед инициализацией систем с `rand()` применить seed.

## 5. Риски / ограничения (честно)

- Точное совпадение *порядка* вызовов `rand()` между клиентами критично и хрупко:
  любой условный `rand()` по разному dt/событию рассинхронизирует. Это главный риск.
- Динамика останется локальной; полная идентичность «кадра» недостижима без
  fixed-timestep (отдельная, большая работа).
- Миссионный прогресс уже реплицируется (`MissionSyncState`, задача A3).

## 6. Критерий «готово»

Два клиента на одном сервере входят в один уровень → статический состав мира
(модели в слотах, цвета, педы, парковка, пропсы) совпадает. Позиции игроков
и их транспорта синхронизируются (уже работает). Динамика допустимо расходится
незначительно.

## 7. Решения и направление реализации (2026-10-24, после аудита)

По итогам глубокого аудита всех систем состояния мира (субагенты, см.
`MULTIPLAYER_SYNC_MANIFEST.ru.md`) приняты четыре решения, которые и задают
очередной этап работ:

1. **Расширить NPC/трафик на всех игроков.** Почти все NPC-/трафик-системы
   захардкожены под `GetAvatarForPlayer(0)` (140 мест): педы, трафик, реакции,
   спавн ориентируются только на первого игрока. Необходимо ввести обход всех
   подключённых игроков (аватаров) в этих точках — это база для того, чтобы мир
   «жил» вокруг любого игрока, а не только player 0.
2. **Host-авторитетный расчёт + рассылка событий** вместо чисто-детерминирован­
   ного воспроизведения. Масса кода зависит от `rand()` (цвет машины, импульс
   удара, выбор педа-водителя), поэтому детерминированное повторение на всех
   клиентах ненадёжно. Расчёт ведётся на хосте, результат рассылается.
3. **Зафиксировать манифест синхронизации** как документ
   `docs/MULTIPLAYER_SYNC_MANIFEST.{ru,}.md` — единый источник правды о том,
   какие функции/состояния мира необходимо синхронизировать (с путями
   файл:строка и приоритетами).
4. **Задействовать готовый транспорт** (`PID_USER`/`SendCustomEvent` и
   `MissionSyncState`) под мировые события: построить каркас event-релея, через
   который разрушаемость, состояние пропсов-дверей, взрывы/остовы, монеты и
   миссионный прогресс распространяются между игроками.

Этапность: (1) → (3) → (4), со сборкой и тестами после каждого подшага.
